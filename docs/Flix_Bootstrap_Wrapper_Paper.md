# A General Repository-Local Bootstrap Wrapper for Flix Projects

## Design, Evidence to Date, and Delta Implementation Plan

**Werner Stein**  
**Revised design paper**  
**11 August 2026**

## Abstract

Flix combines compilation, dependency management, testing, packaging, publishing, and language-server support in one JVM application. A newly cloned project nevertheless requires an external Java runtime and a suitable `flix.jar`. The manifest already contains a compiler declaration, although the Flix documentation states: “The `flix` field is not yet used, but it will be used in the future” [2]. This paper proposes a general repository-local bootstrap convention generated by an official `flix wrapper` command. The generated artifacts are a small POSIX `flix` script, a PowerShell `flix.ps1` implementation, a minimal `flix.bat` trampoline, and `.gitattributes` rules.

The wrapper reads the project compiler version from `flix.toml`, selects Java by explicit and familiar precedence, verifies a pinned SHA-256 digest, installs the compiler atomically into an overridable user cache, and forwards the remaining arguments to the official CLI. It does not rank LTS releases, download a JDK, resolve dependencies, or reproduce Flix commands. The existing `wstein/flix-invaders` `bin/flix` script is treated as an ad-hoc predecessor and evidence source, not as the proposed general wrapper. This revision presents an implementation plan rather than claiming completed validation. It also confronts the strongest alternative: a version-aware global `flix` executable would provide better overall ergonomics, while the repository wrapper uniquely preserves clone-with-no-Flix-installed operation.

**Keywords:** Flix, bootstrap wrapper, reproducible builds, software supply chain, JVM, TOML, developer experience

## 1. Introduction and Current Evidence

For Gradle, Maven, and Mill projects, `./gradlew`, `./mvnw`, and `./mill` make the repository itself the stable entry point. Flix already owns nearly all build semantics after `flix.jar` starts. The remaining problem is to select a compiler and Java runtime safely enough that a contributor can run:

```console
git clone https://github.com/example/a-flix-project
cd a-flix-project
./flix test
```

The real `wstein/flix-invaders` manifest demonstrates the intended authority:

```toml
[package]
name = "flix-invaders"
version = "0.1.4"
flix = "0.75.2"
```

That repository already contains a 37-line `bin/flix` convenience script used by its three operating-system workflows. It is not the general wrapper proposed here: it has a nonstandard location, repo-local cache, POSIX-only implementation, and no generation or upgrade contract. It is nevertheless valuable adverse evidence. A simple line-oriented extractor can misread a trailing comment, fail open when extraction is empty, select a key from the wrong TOML table, race on a fixed temporary filename, omit digest verification, and expose an opaque JVM compatibility failure. Green CI does not exercise all bootstrap failure modes. The proposed wrapper replaces that ad-hoc predecessor and turns these observed weaknesses into normative tests.

The deliverable is intentionally bounded. The generated POSIX launcher should remain at or below 150 lines, the PowerShell implementation at or below 120 lines, and the Batch trampoline at or below 10 lines excluding comments and license text. These are budgets, not targets.

## 2. Related Work and Roadmap Alignment

### 2.1 Existing Flix responsibility

Flix requires Java 21 or newer and already parses the complete manifest, resolves packages, checks, tests, runs, builds, and publishes projects [1]–[5]. The wrapper therefore has no legitimate reason to understand dependency graphs, source layouts, Processing, Datalog, or command-specific options.

Issue #4380 explicitly describes a `flix` shim whose primary task is to locate, and possibly download, the appropriate JAR [10]. Issue #11436 records package-manager principles centered on user experience, transparent actions, safe downloads, and actionable errors [11]. Issue #13003 asks whether the toolchain should honor the manifest compiler field and provide setup or diagnostic behavior [17]. Together they support the problem statement, but they do not constitute maintainer approval of this particular implementation.

Issue #11150 contains a narrower observation: a command run one directory below the project should look one directory upward for `flix.toml` [12]. It does not specify Cargo-style traversal. This paper generalizes the requirement explicitly and labels that generalization as a proposal. Issue #12208 reinforces that manifest formatting and mutation belong to Flix, not to a shell wrapper [13]. Distribution proposals #13002 and #4561 could eventually make raw GitHub downloads unnecessary [18], [19].

Issue #11436 was opened by Jakob Schneider (`jaschdoc`) on 27 August 2025. Its body discloses that the post was created experimentally with GitHub Copilot. It remains useful roadmap evidence, but not a uniquely authoritative statement of team policy. Issue #4561 was opened by Oliver Weiler (`helpermethod`).

### 2.2 Gradle and Mill

Gradle demonstrates repository-local generation, explicit distribution checksums, wrapper upgrades, and CI validation of committed wrapper artifacts [6], [7]. Mill demonstrates a script-centered, zero-setup launcher [8], [9]. The proposed Flix shape borrows the entry-point convention, not either tool's build semantics.

### 2.3 The strongest alternative

A globally installed, version-aware `flix` that reads `flix.toml`, fetches the requested compiler, and serves both CLI and editor is superior on several axes: it supports `flix init`, leaves no generated scripts in repositories, avoids implementing TOML in shell, and can centralize policy in Scala. This appears consistent with the global distribution direction in #4561 and #13002. It loses one property: a clean machine cannot bootstrap from a clone without first installing Flix.

The repository wrapper is therefore best treated as a small, replaceable Level 1 mechanism. Its most mergeable upstream form is an official `flix wrapper` generator. If a global version-aware launcher becomes authoritative, generated scripts can become thin delegates or disappear.

## 3. Normative Requirements

### 3.1 Functional requirements

**FR1 — Generated repository entry point.** An official `flix wrapper [--flix-version X]` compiler command shall generate or update `flix`, `flix.ps1`, `flix.bat`, and the required `.gitattributes` entries. Generated files shall identify their wrapper version, source, and permissive vendoring license.

**FR2 — Manifest authority.** `[package].flix` is the human-maintained compiler-version authority. Generated digest metadata is permitted because it is mechanically derived and verified; no second user-edited wrapper configuration file is introduced.

**FR3 — Project root.** The launcher shall resolve only the symlink chain of its own file and then search upward for the nearest `flix.toml`, stopping at the first match or a Git work-tree boundary. Multiple nested manifests therefore use nearest-ancestor semantics. A repository with independent nested projects uses one generated launcher per intended manifest boundary.

**FR4 — TOML compatibility.** Extraction shall accept every TOML 1.0 spelling that Flix accepts for this field, including whitespace, comments, quoted or bare dotted keys, `[ package ]`, `package.flix = ...`, and basic, literal, multiline-basic, or multiline-literal strings where the resulting value is valid. It shall track lexical state `none | basic | literal | ml-basic | ml-literal`, reject duplicate or genuinely ambiguous assignments, and never evaluate content.

**FR5 — Exact release identifier.** Until Flix defines range semantics, the wrapper shall require an exact compiler identifier. It shall accept optional prerelease and build metadata, reject `..` and path separators independently, and place `--` before operands passed to utilities that support an end-of-options marker.

```text
[0-9]+\.[0-9]+\.[0-9]+(?:-[0-9A-Za-z](?:[0-9A-Za-z.-]*[0-9A-Za-z])?)?(?:\+[0-9A-Za-z](?:[0-9A-Za-z.-]*[0-9A-Za-z])?)?
```

Accepted examples are `0.75.2`, `0.76.0-rc.1`, `0.75.2+build.4`, and `1.2.3-beta.2+build.17`. Rejected examples include `v0.75.2`, `0.75`, `0.75.2+`, `1.0.0-../../../foo`, ranges, wildcards, slash or backslash, and any value containing `..`. Build metadata is accepted but stripped when forming the canonical Flix release tag and shared artifact-cache key; the full manifest value remains visible in diagnostics.

**FR6 — Java selection.** Selection order shall be `FLIX_JAVA_HOME` → `JAVA_HOME` → compatible `java` on `PATH` → newest compatible platform-discovered installation. There is no LTS ranking table and no per-project Java-selection file. Every candidate is executed to determine its feature version. A wrapper-release constant defines the tested interval; the initial proposal is Java 21 through 26, subject to the Flix CI matrix. An explicit incompatible candidate fails rather than being silently ignored. When discovery selects a Java other than the `PATH` executable, the wrapper prints one concise notice to stderr.

**FR7 — Verified compiler acquisition.** The generated wrapper shall contain a pinned SHA-256 for the compiler selected when the wrapper was generated. Before every execution it verifies the cached JAR. A mismatch causes removal from consideration and reacquisition; the unverified bytes are never executed. GitHub's release API supplies per-asset SHA-256 metadata, and for Flix 0.75.2 the reported `flix.jar` digest has been independently matched to the cached artifact:

```text
sha256:a2697d875725a0dde6e793b8d54cb220e86167a6d49ec5f0ccb0832966c8c15a
```

**FR8 — Atomic, lock-free cache.** Cache population uses a uniquely created temporary file in the destination filesystem, verifies it, and renames it atomically. Concurrent valid writers are harmless; last-writer-wins is correct for immutable content-addressed bytes. No stale lock protocol or `flock(1)` dependency is introduced.

**FR9 — Cache and distribution overrides.** `FLIX_CACHE_HOME` overrides platform defaults; `FLIX_JAR` bypasses acquisition for a locally built compiler after readability checks; and `FLIX_DIST_URL` selects an approved mirror base. The default cache is outside tracked repository paths. Standard `HTTPS_PROXY`, `https_proxy`, and `NO_PROXY` conventions are honored where the downloader supports them. A documented offline procedure pre-populates the cache with a verified artifact.

**FR10 — Transparent execution.** All non-wrapper arguments and the compiler exit status are forwarded without a command allow-list. The only reserved command namespace is `./flix wrapper ...`; diagnostic and maintenance operations are `./flix wrapper doctor`, `setup`, and `pin`. `./flix --wrapper-version` reports the generated wrapper version. Wrapper-defined failures use stable exit codes distinct from normal compiler results and from shell conventions 126 and 127.

**FR11 — JVM options.** `FLIX_JVM_OPTS` is parsed according to one documented cross-platform convention. `JAVA_OPTS` may be appended only if the compatibility and quoting contract is explicit. The wrapper does not silently reinterpret arbitrary shell syntax embedded in either variable.

**FR12 — Windows implementation.** `flix.bat` is a minimal trampoline to `flix.ps1`. PowerShell owns manifest parsing, download, cache, and process invocation; its `$args` array preserves argument boundaries. Batch cannot promise byte-for-byte parity because `%`, `!`, `^`, quoting, Ctrl-C, and the absence of `exec` impose structural deviations. The conformance contract documents those deviations rather than claiming impossible equivalence.

**FR13 — Line endings and mode.** Generated `.gitattributes` shall include `/flix text eol=lf`, `/flix.ps1 text eol=crlf`, and `/flix.bat text eol=crlf`. Generation shall set the POSIX executable bit and document `git update-index --chmod=+x flix`; archive downloads that discard the bit require an explicit recovery instruction.

**FR14 — Editor boundary.** The initial scope is the CLI. The VS Code extension may acquire its own compiler and can therefore disagree with the project pin. An upstream integration ask shall permit the extension to invoke the project launcher or share the same version-resolution service.

### 3.2 Non-functional requirements

- Warm-path overhead shall be measured against direct `java -jar`, with a target below 50 ms excluding JVM startup.
- HTTPS downloads shall use failure-on-HTTP-error, retry limits, connection and total timeouts, and HTTPS-only initial and redirected protocols.
- A successful hash is the authenticity test. ZIP magic is not treated as integrity evidence; at most it improves an error message.
- The wrapper shall not download a JDK, modify `flix.toml`, resolve dependencies, alias Flix commands, or contain application-specific behavior.
- POSIX and PowerShell implementations shall be generated from one behavioral contract and shared fixtures.

## 4. Architecture

### 4.1 Responsibility boundary

```text
Generated wrapper
  ├─ find nearest project manifest
  ├─ read the exact compiler identifier
  ├─ select a tested Java runtime
  ├─ verify or acquire the pinned compiler artifact
  └─ start Flix with preserved arguments

Official Flix CLI
  ├─ parse and mutate the complete manifest
  ├─ resolve dependencies
  ├─ check, test, run, build, and publish
  ├─ implement setup/doctor if adopted upstream
  └─ generate and upgrade wrapper artifacts
```

This boundary is the primary invariant and should remain unchanged even if the transport moves from GitHub Releases to Maven Central.

### 4.2 Files, cache, and provenance

Committed files are `flix.toml`, `flix`, `flix.ps1`, `flix.bat`, and `.gitattributes`. The wrapper scripts include a wrapper format/version stamp, compiler digest, generator provenance, and license header. Machine state resides under:

```text
Linux:   ${FLIX_CACHE_HOME:-${XDG_CACHE_HOME:-$HOME/.cache}/flix}
macOS:   ${FLIX_CACHE_HOME:-$HOME/Library/Caches/flix}
Windows: ${FLIX_CACHE_HOME:-%LOCALAPPDATA%\Flix}
```

CI may set `FLIX_CACHE_HOME` to a workflow cache path. A downloaded JAR may be under a repository only when the directory is explicitly untracked; the general default is user-level sharing.

### 4.3 TOML reader

The bootstrap paradox rules out using the target compiler to read its own version. A narrow reader is acceptable only if it is a real lexical state machine for this field. The motivating failure is concrete:

```toml
flix = "0.75.2" # pinned
```

A shipped ad-hoc extractor anchored on the closing quote can capture the whole line or produce an empty value. A multiline string containing `flix = "6.6.6"` can also fool a reader without string state. The test oracle should therefore compare both implementations against a standards-compliant TOML parser over a corpus of public `flix.toml` files. Phase 0 also asks Flix maintainers whether the formatter will commit to a stable canonical spelling; such a guarantee could simplify future generated wrappers without narrowing current compatibility.

### 4.4 Java resolution

The wrapper respects explicit user configuration before discovery. `PATH` is the normal implicit choice and stays silent when compatible. Platform discovery is a last resort and may inspect `/usr/libexec/java_home`, standard Linux JVM directories, Windows registry views, and conventional vendor locations. Only the selected fallback is reported; exhaustive candidate reasons remain behind verbose output.

No LTS preference exists. LTS status is not a project requirement, changes over time, and could silently diverge from both `PATH` and CI. A minimum and tested ceiling are operational compatibility bounds, not claims that every newer JDK is broken. The ceiling must be updated only after CI verifies relevant Flix JVM interop, including class loading, AWT/Processing, JNI, and restricted native-access behavior.

### 4.5 Download and cache transaction

1. Derive a canonical release coordinate after validating and normalizing the identifier.
2. Select `FLIX_JAR`, an already verified cache entry, or the configured/default distribution origin.
3. Create a unique temporary file in the final cache directory.
4. Download with HTTPS-only redirects, bounded retries, and timeouts.
5. Compute SHA-256 and compare it with the generated pin.
6. Atomically rename the verified file into place; tolerate a concurrent valid winner.
7. Recompute the digest on every run before execution.

Content length may diagnose truncation but never replaces the digest. `curl -f` rejects HTTP error pages; ZIP magic alone proves almost nothing because a truncated JAR retains its first local-file header.

### 4.6 Windows contract

`flix.bat` performs only PowerShell discovery and trampoline invocation. `flix.ps1` receives `$args` as an array and implements the shared contract. Windows 10 1803 and later generally include `curl.exe`, but availability is tested rather than assumed; a PowerShell downloader must specify proxy behavior explicitly. The test report records unavoidable Batch behavior for Ctrl-C and characters consumed by `cmd.exe` before the trampoline starts.

## 5. Security and Supply-Chain Model

The wrapper executes before project build logic and is itself a supply-chain target. Controls fall into two independent layers.

**Compiler artifact controls:** exact identifier validation, HTTPS-only transport, pinned SHA-256, verification on every run, unique temporary files, atomic installation, overridable mirror/cache, and offline pre-population.

**Wrapper artifact controls:** official generation, a version/provenance header, permissive vendoring license, upstream-published SHA-256 values for official generated files, and a CI validation check analogous to Gradle Wrapper Validation. A pull request modifying `flix`, `flix.ps1`, or `flix.bat` must trigger this check. Digest pinning the compiler does not protect a maliciously modified launcher.

The Flix 0.75.2 digest evidence removes the earlier claimed checksum gap. The open upstream question is not whether a digest exists, but which API or published manifest is the stable contract and how generated wrappers and mirrors consume it.

## 6. Evidence to Date and Proposed Validation

### 6.1 Evidence already available

- `wstein/flix-invaders` is a normal `flix.toml` application and has used its ad-hoc `bin/flix` in Ubuntu, macOS, and Windows workflows since 6 August 2026 [16].
- The script demonstrates that version-directed acquisition and warm-cache operation are practical, while its extractor, temporary-file, digest, and Java diagnostics expose failure modes the general contract must prevent.
- GitHub release metadata for `v0.75.2` reports a SHA-256 digest that matches the repository's cached JAR byte-for-byte.

These observations motivate the design. They do not validate the proposed POSIX, PowerShell, or generator implementation, which does not yet exist.

### 6.2 Falsifiable evaluation questions

1. Does the TOML extractor accept every publicly discoverable `flix.toml` whose `[package].flix` value is legal and exact?
2. Does warm-path wrapper overhead remain below 50 ms relative to direct `java -jar`, excluding JVM startup?
3. Which argument vectors survive POSIX and PowerShell unchanged, and which vectors are irrecoverably altered by the Batch trampoline?
4. Does a truncated, corrupt, or concurrently populated cache recover without executing unverified bytes?

### 6.3 Measurements

Report cold wall-clock time, warm-path overhead, bytes transferred, recovery time after a truncated cache, extractor corpus acceptance, and argument-vector deviations. Repository file count and lines of code are reported as costs, not success metrics.

## 7. Delta Implementation Plan

### Phase 0 — Obtain policy decisions before implementation

Open a concise comment or RFC linked to #13003. Ask maintainers to decide:

1. Is `[package].flix` an exact compiler contract, or may it contain ranges?
2. Which release API or manifest is the stable URL-and-digest contract?
3. Do `setup` and `doctor` belong to the compiler, the generated wrapper namespace, or both?
4. May the VS Code extension use the project launcher or shared resolver?
5. Will upstream publish hashes for official wrapper artifacts and support a validation action?
6. Will the Flix formatter guarantee a stable spelling for `[package].flix`?

Record the answer or explicitly record that the prototype proceeds with exact versions and the contract in this paper. This replaces the former impossible gate that required approval before the first upstream contact.

### Phase 1 — Specify generator output and provenance

1. Define wrapper format version, source URL, license, and generated-file headers.
2. Define `flix wrapper`, `flix wrapper --flix-version X`, and upgrade behavior.
3. Define the embedded compiler digest and how generation verifies it against release metadata.
4. Define `.gitattributes` entries and executable-bit instructions.
5. Enforce the line budgets in CI.

**Gate:** two independently generated copies from identical inputs are byte-for-byte equal.

### Phase 2 — Build shared fixtures and the TOML oracle

1. Implement fixtures for comments, indentation, quoted keys, `[ package ]`, dotted keys, four string forms, BOM, CRLF, multiline decoys, duplicates, and ambiguity.
2. Include the observed trailing-comment and empty-extraction failures.
3. Search public repositories for `flix.toml`, retain license-compatible minimized cases, and report corpus acceptance.
4. Compare POSIX and PowerShell results to a standards-compliant TOML parser.
5. Add exact identifier fixtures, including build metadata and traversal attempts.

**Gate:** every accepted corpus manifest yields the oracle value; every ambiguous or unsafe fixture fails before URL or path construction.

### Phase 3 — Implement root discovery and overrides

1. Resolve the launcher file's symlink chain only while each target is a file.
2. Search upward for the nearest `flix.toml` and stop at the Git boundary.
3. Implement `FLIX_JAR`, `FLIX_CACHE_HOME`, and `FLIX_DIST_URL`.
4. Specify nested-manifest behavior and invocation from subdirectories.

**Gate:** real-directory, symlinked-file, symlinked-directory, nested-manifest, and Git-boundary fixtures resolve predictably.

### Phase 4 — Implement bounded Java selection

1. Implement `FLIX_JAVA_HOME` → `JAVA_HOME` → `PATH` → platform discovery.
2. Parse feature versions from the candidate executable, require the configured interval, and fail explicitly for invalid explicit choices.
3. Print a one-line notice only when discovery overrides the `PATH` outcome.
4. Cover Java 21–26 and incompatible-below/above fixtures in CI.
5. Forward documented JVM options without `eval`.

**Gate:** the same environment produces the same choice, direct and wrapper invocations use the same `PATH` Java when compatible, and warm discovery does not enumerate unrelated JVMs.

### Phase 5 — Implement verified lock-free acquisition

1. Pin the release digest during wrapper generation.
2. Implement HTTPS-only download, bounded retry/connect/total time, and proxy behavior.
3. Verify cache entries on every execution.
4. Use destination-local unique temporary files and atomic rename without locks.
5. Test corruption, truncation, digest mismatch, concurrent population, mirror use, and offline pre-population.

**Gate:** no unverified byte sequence reaches `java -jar`; two concurrent cold starts converge on one verified artifact.

### Phase 6 — Implement execution surfaces

1. Implement the POSIX launcher with `exec`; use `--` for downloader and filesystem operands wherever the called utility supports it.
2. Implement all Windows logic in `flix.ps1` and keep `flix.bat` as a trampoline.
3. Implement only `wrapper doctor|setup|pin` plus `--wrapper-version`.
4. Allocate wrapper exit codes and preserve compiler exit status otherwise.
5. Record Batch deviations instead of claiming perfect parity.

**Gate:** the argument corpus passes on POSIX and PowerShell; every Batch deviation is reproduced and documented.

### Phase 7 — Validate in `flix-invaders` and additional projects

1. Replace or explicitly deprecate `bin/flix` so the repository never presents two unexplained wrappers.
2. Run `check`, headless tests, and a bounded graphical smoke test on Ubuntu, macOS, and Windows.
3. Validate a library, a CLI application, a nested project, and a project with transitive packages.
4. Measure cold time, warm overhead, bytes, and corrupt-cache recovery.
5. Test clean clone, GitHub archive line endings/mode recovery, paths with spaces and Unicode, and CI caching through `FLIX_CACHE_HOME`.

**Gate:** results are published with failures and deviations, not summarized as a binary “validated” claim.

### Phase 8 — Upstream generator and transition

1. Submit the generator, contract, fixtures, and wrapper-validation mechanism upstream if maintainers accept the direction.
2. Add a language-server integration path or state the CLI-only limitation prominently.
3. Define wrapper upgrade and deprecation policy.
4. If a global version-aware launcher supersedes bootstrap logic, regenerate scripts as thin delegates and remove redundant policy from shell and PowerShell.

## 8. Deliberately Not Implemented

- JDK download: vendor, license, archive, signature, update, and platform policy require a separate proposal.
- LTS ranking: it silently changes the user's JVM and adds time-dependent policy without a project requirement.
- Cache locks: immutable verified artifacts make unique temporary files plus atomic rename sufficient.
- Bare `setup` or `doctor`: these names may become official Flix commands under #13003.
- Dependency, build, and command interpretation: these remain Flix responsibilities.
- Manifest rewriting: generation may verify the pin but only Flix's parser/formatter should edit `flix.toml`.
- ZIP-magic integrity checks: SHA-256 provides the security property.

## 9. Risks and Adverse Evidence

The shim goal has existed since 2022 without an official implementation. Plausible explanations include maintainer bandwidth, preference for a global distribution model, and reluctance to own cross-platform shell code. The proposal should not assume that absence proves demand for repository wrappers. It should instead make the disposable layer cheap and move durable policy into the Flix generator or global launcher.

The narrow TOML reader is the largest compatibility risk. A general wrapper encounters manifests it did not author; fail-closed behavior protects security but can still reject valid projects. Corpus validation and an eventual parser implemented in Flix are the mitigations.

The tested Java ceiling is also maintenance. Java 24 and later increasingly restrict unsafe or native interaction, and the next scheduled LTS transition after Java 25 is Java 29 in September 2027 [14], [15]. The wrapper should not encode LTS status; maintainers update the tested ceiling from CI evidence.

Corporate proxies, mirrors, air-gapped use, read-only homes, archive downloads, nested repositories, and modified generated scripts are ordinary deployment conditions, not edge cases. Each has a requirement and test above.

## 10. Conclusion

A general Flix bootstrap wrapper is justified only if it stays smaller than the policy it may eventually replace. The corrected design uses an official generator, manifest-directed exact compiler selection, pinned SHA-256 verification, lock-free atomic caching, familiar Java precedence with a tested ceiling, PowerShell rather than Batch for Windows logic, and explicit escape hatches for local compilers, mirrors, caches, and JVM options.

The existing `flix-invaders` shim supplies evidence and failure cases, not completed validation. The next useful artifact is therefore not another greenfield script: it is a maintainer decision on the launcher contract, followed by generated implementations and falsifiable cross-platform measurements. If Flix adopts a global version-aware launcher, the repository entry point can become a thin delegate. That outcome would be a successful transition, not a failure of the wrapper proposal.

## Appendix A. Normative Selection Pseudocode

```text
wrapper_file := resolve_file_symlink_chain(argv0)
root := nearest_manifest_ancestor(wrapper_file.parent, stop = git_boundary)
manifest_version := read_package_flix_with_toml_state_machine(root / "flix.toml")
release_version := validate_and_strip_build_metadata(manifest_version)

if env("FLIX_JAR") exists:
    jar := validate_local_override(env("FLIX_JAR"))
else:
    cache := resolve_cache(env("FLIX_CACHE_HOME"), platform_default)
    jar := verify_cached(cache, release_version, embedded_sha256)
        or download_to_unique_temp_and_verify(release_version, embedded_sha256)
        or fail(FLIXW005)

java := validate_explicit(env("FLIX_JAVA_HOME"))
     or validate_explicit(env("JAVA_HOME"))
     or compatible_java_on_path()
     or newest_compatible(platform_discovery(), minimum = 21, maximum = tested_ceiling)
     or fail(FLIXW003)

chdir(root)
exec_or_spawn(java, jvm_options, "-jar", jar, original_arguments)
```

## Appendix C. Stable Wrapper Errors and Exit Codes

| Identifier | Exit | Meaning |
|---|---:|---|
| `FLIXW001` | 80 | no `flix.toml` found before the project boundary |
| `FLIXW002` | 81 | compiler field missing, ambiguous, unsupported, or unsafe |
| `FLIXW003` | 82 | no Java in the supported interval |
| `FLIXW004` | 83 | explicit Java selection is invalid or incompatible |
| `FLIXW005` | 84 | compiler acquisition failed |
| `FLIXW006` | 85 | compiler digest validation failed |
| `FLIXW007` | 86 | cache unavailable or atomic installation failed |
| `FLIXW008` | 87 | wrapper environment or option value is malformed |
| `FLIXW009` | 88 | wrapper namespace or generator usage error |

Compiler exit codes are returned unchanged. Codes 126 and 127 remain reserved for conventional shell execution failures.
